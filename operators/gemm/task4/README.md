# TASK4：CUDA SGEMM 实现与性能分析

## 1. 实验环境

| 项目 | 配置 |
|---|---|
| GPU | NVIDIA RTX 5070 Ti |
| CUDA Toolkit | 13.0 |
| GPU 架构 | sm_120 |
| SM 数量 | 70 |
| FP32 FMA 参考吞吐量 | 49.33 TFLOPS |

## 2. 实验目标

使用 CUDA C++ 实现 FP32 SGEMM，结合 Shared Memory Tiling（共享内存分块）、Register Tiling（寄存器分块）和 `float4` 向量化加载，分析不同分块参数对性能及硬件资源使用的影响。

## 3. Kernel 实现

计算公式：

`C = alpha × A × B + beta × C`

主要实现：

- 每个 Block 负责 BM×BN 的输出分块。
- 每个线程使用 TM×TN 个寄存器累加器。
- A、B 使用 `float4` 从 Global Memory 加载。
- A 在 Shared Memory 中采用转置布局 `sA[BK][BM]`，B 使用 `sB[BK][BN]`。
- 沿 K 方向分块，使用 FMA 完成每线程 TM×TN 外积累加。
- 使用 `__syncthreads()` 保证共享内存数据的加载与读取顺序。

## 4. 实验方法

测试三组配置：

| 配置 | BM | BN | BK | TM | TN | Threads/Block |
|---|---:|---:|---:|---:|---:|---:|
| A | 128 | 128 | 8 | 8 | 8 | 256 |
| B | 128 | 128 | 16 | 8 | 8 | 256 |
| C | 256 | 256 | 16 | 8 | 8 | 1024 |

测试矩阵规模为 N=256、512、1024 和 4096。

使用 CUDA Event 计时，预热 4 次、重复测量 4 次，计算平均执行时间和 TFLOPS。

N=256、512、1024 使用 CPU SGEMM 计算参考结果，并统计最大绝对误差；N=4096 仅测试性能。

## 5. 实验结果

### 5.1 SGEMM 性能

单位：TFLOPS。

| 矩阵规模 | 配置 A | 配置 B | 配置 C |
|---|---:|---:|---:|
| 256×256 | 0.875 | 0.963 | 0.063 |
| 512×512 | 4.025 | 4.376 | 0.142 |
| 1024×1024 | 17.322 | 18.947 | 0.578 |
| 4096×4096 | 25.143 | **27.766** | 1.453 |

N=4096 时：

| 配置 | 时间 | TFLOPS |
|---|---:|---:|
| A：128×128，BK=8 | 5.466 ms | 25.143 |
| B：128×128，BK=16 | 4.950 ms | **27.766** |
| C：256×256，BK=16 | 94.607 ms | 1.453 |

配置 B 为当前三组参数中实测性能最高的版本，达到 27.766 TFLOPS，约为 TASK2 FP32 FMA 参考吞吐量的 56.3%。

### 5.2 正确性检查

三组配置的最大绝对误差相同：

| 矩阵规模 | Max Error |
|---|---:|
| 256×256 | 2.28881e-5 |
| 512×512 | 4.57763e-5 |
| 1024×1024 | 9.155273e-5 |

结果与 CPU 参考计算较为接近。

当前测试仅统计最大绝对误差，尚未设置自动 PASS/FAIL 阈值，因此不将其表述为严格的正确性验证通过。

### 5.3 寄存器资源分析

使用 `nvcc -Xptxas=-v` 检查配置 B、C 的编译器资源报告。

| 指标 | 配置 B | 配置 C |
|---|---:|---:|
| Threads/Block | 256 | 1024 |
| Registers/Thread | 115 | 64 |
| Spill Stores | 0 B | 2172 B |
| Spill Loads | 0 B | 2168 B |
| Stack Frame | 0 B | 616 B |
| Shared Memory | 16 KiB | 32 KiB |

配置 B 无寄存器溢出。

配置 C 每个 Block 需要 1024 个线程，寄存器资源压力较大。编译器产生了明显的寄存器溢出，需要通过 Local Memory（局部内存）保存部分数据。

配置 C 的吞吐量仅为 1.453 TFLOPS，约为配置 B 的 5.2%。

寄存器溢出是性能下降的重要原因，但其具体运行时开销尚未通过 NCU 动态指标量化。

### 5.4 分块参数分析

**BK 的影响**

在 BM=BN=128、TM=TN=8 不变时，将 BK 从 8 增加到 16，N=4096 的吞吐量由 25.143 TFLOPS 提升至 27.766 TFLOPS，提升约 10.4%。

**BM、BN 的影响**

在 BK=16、TM=TN=8 不变时，将 BM、BN 从 128 增大到 256，使每个 Block 的线程数从 256 增加到 1024。

尽管更大的分块具有更高的数据复用潜力，但寄存器资源压力和溢出导致实际性能显著下降。

## 6. 实验结论

1. 完成 FP32 SGEMM 的 Shared Memory Tiling、Register Tiling 和 `float4` 向量化加载实现。
2. 当前三组配置中，BM=BN=128、BK=16、TM=TN=8 的性能最高，达到 **27.766 TFLOPS**。
3. 增大 BK 能在当前配置下提高性能，但提升幅度需要通过实际 Benchmark 确认。
4. 过大的 Block Tile 会增加资源压力。BM=BN=256 配置发生明显寄存器溢出，性能大幅下降。
5. SGEMM 分块参数需要综合考虑数据复用、线程数量及寄存器资源，不能仅根据理论计算访存比选择。
